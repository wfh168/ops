```

- 不同团队负责不同服务

我们通过Nacos、RabbitMQ、Docker等技术来解决这些问题。
```

**回答要点：**
```
【编写Dockerfile】
- 使用多阶段构建，构建阶段用maven镜像，运行阶段用JRE镜像

【部署流程】
1. Jenkins构建完成后，打包Docker镜像
2. 推送镜像到私有仓库（或Docker Hub）
3. SSH连接到服务器
4. 拉取最新镜像
5. docker-compose up -d 启动服务
6. 健康检查确认服务正常

【优势】
- 环境一致性，开发、测试、生产环境完全一样
- 部署简单，一键启动所有服务
- 资源隔离，互不影响
```

#### 4. MySQL主从复制是怎么配置的？读写分离怎么实现？

**回答要点：**
```
【主从复制配置】
1. 主库配置：
   - 开启binlog日志
   - 设置server-id
   - 创建复制用户

2. 从库配置：
   - 设置不同的server-id
   - 配置主库信息（IP、端口、用户、密码）
   - 启动slave进程

3. 验证：
   - show slave status 查看复制状态
   - 主库写入数据，从库能同步

【读写分离实现】
方式1：应用层实现
- 使用MyBatis-Plus的动态数据源
- 写操作走主库，读操作走从库
- 代码中通过注解或配置指定数据源

方式2：中间件实现（更推荐）
- 使用MyCat或ShardingSphere
- 应用无需改代码
- 中间件自动路由读写请求

【注意事项】
- 主从延迟问题：重要数据读主库
- 从库故障：自动切换到主库
- 监控复制状态，及时发现问题
```

#### 5. Redis哨兵模式是怎么配置的？

**回答要点：**
```
【哨兵模式架构】
- 1个主节点 + 2个从节点
- 3个哨兵节点（奇数个，方便选举）

【配置步骤】
1. 配置Redis主从：
   - 主节点正常配置
   - 从节点配置 replicaof 指向主节点

2. 配置哨兵：
   - 创建sentinel.conf
   - 配置监控的主节点信息
   - 设置quorum（多少个哨兵认为主节点下线才算下线）
   - 启动哨兵进程

【工作原理】
- 哨兵监控主节点健康状态
- 主节点故障时，哨兵自动选举新的主节点
- 其他从节点自动切换到新主节点
- 应用通过哨兵连接Redis，自动感知主节点变化

【优势】
- 高可用：主节点故障自动切换
- 监控：实时监控Redis状态
- 通知：故障时自动告警

【应用连接】
- 不直接连接Redis，而是连接哨兵
- 哨兵返回当前主节点地址
- 主节点切换时，应用自动感知
```

#### 6. Nginx负载均衡是怎么配置的？

**回答要点：**
```
【配置示例】
upstream backend {
    # 负载均衡策略：轮询（默认）
    server 192.168.1.10:8080 weight=1;
    server 192.168.1.11:8080 weight=1;
    server 192.168.1.12:8080 weight=2;  # 权重更高
    
    # 健康检查
    check interval=3000 rise=2 fall=3 timeout=1000;
}

server {
    listen 80;
    server_name api.example.com;
    
    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

【负载均衡策略】
1. 轮询（默认）：依次分配请求
2. weight：按权重分配，性能好的服务器权重高
3. ip_hash：同一IP的请求分配到同一台服务器（解决session问题）
4. least_conn：分配给连接数最少的服务器

【健康检查】
- 定期检查后端服务器状态
- 服务器故障时自动摘除
- 服务器恢复后自动加入

【我们的配置】
- 使用weight策略，根据服务器性能分配权重
- 配置健康检查，3秒检查一次
- 失败3次标记为down，成功2次标记为up
```

#### 7. Nacos和Sentinel分别是做什么的？

**回答要点：**
```
【Nacos - 服务注册与配置管理】

作用1：服务注册与发现
- 微服务启动时注册到Nacos
- 服务间调用时从Nacos获取服务地址
- 服务下线时自动从Nacos移除

作用2：配置管理
- 统一管理所有服务的配置
- 配置修改后实时推送到服务
- 支持不同环境的配置（dev、test、prod）

优势：
- 不用硬编码服务地址
- 配置修改不用重启服务
- 支持配置版本管理和回滚

【Sentinel - 流量控制与熔断降级】

作用1：流量控制（限流）
- 限制接口的QPS（每秒请求数）
- 防止流量突增导致系统崩溃
- 支持多种限流策略（QPS、线程数、慢调用）

作用2：熔断降级
- 服务调用失败达到阈值时，自动熔断
- 熔断期间直接返回降级结果，不再调用
- 一段时间后尝试恢复

作用3：系统保护
- 监控系统负载、CPU、内存
- 负载过高时自动限流保护

【实际应用】
- 热点接口配置限流规则，QPS限制在1000
- 调用第三方服务配置熔断，失败率超过50%自动熔断
- 配置降级规则，熔断时返回友好提示
```

#### 8. RabbitMQ的死信队列是怎么配置的？

**回答要点：**
```
【什么是死信队列】
消息在以下情况会变成死信：
1. 消息被拒绝（reject/nack）且不重新入队
2. 消息过期（TTL超时）
3. 队列达到最大长度

【配置步骤】
1. 创建死信交换机和死信队列：
   - 死信交换机：dlx.exchange
   - 死信队列：dlx.queue

2. 业务队列绑定死信交换机：
   x-dead-letter-exchange: dlx.exchange
   x-dead-letter-routing-key: dlx.routing.key

3. 消费者监听死信队列，处理失败消息

【实际应用场景】
场景：发送通知消息
1. 消息发送到通知队列
2. 消费者处理失败（比如第三方接口调用失败）
3. 消息进入死信队列
4. 死信队列消费者记录失败日志，人工处理或重试

【优势】
- 不会丢失失败的消息
- 可以分析失败原因
- 支持人工干预或延迟重试
```

#### 9. 响应时间从800ms降到200ms是怎么做到的？

**回答要点：**
```
主要通过三个方面优化：

【1. Redis缓存】
- 热点数据缓存到Redis（文章详情、用户信息）
- 缓存命中率达到80%以上
- 缓存未命中才查数据库

优化效果：
- 查询Redis只需要几毫秒
- 大部分请求不用查数据库

【2. 数据库读写分离】
- 写操作走主库
- 读操作走从库（2个从库）
- 读请求分散到多个数据库

优化效果：
- 减轻主库压力
- 读操作并发能力提升

【3. 数据库索引优化】
- 分析慢查询日志
- 给常用查询字段添加索引
- 优化SQL语句

优化效果：
- 查询时间从几百毫秒降到几十毫秒

【4. 其他优化】
- 使用连接池，减少连接开销
- 异步处理非核心业务（通知、日志）
- 静态资源CDN加速

【监控验证】
- 使用Prometheus监控接口响应时间
- Grafana展示P50、P95、P99指标
- 持续优化慢接口
```

#### 10. Prometheus + Grafana监控了哪些指标？

**回答要点：**
```
【服务器资源监控】
- CPU使用率、内存使用率、磁盘使用率
- 网络流量、磁盘IO
- 告警阈值：CPU > 80%、内存 > 85%、磁盘 > 90%

【容器监控】
- 容器CPU、内存使用情况
- 容器状态（running、stopped、restarting）
- 容器重启次数

【应用监控】
- 接口响应时间（P50、P95、P99）
- 接口QPS（每秒请求数）
- 接口错误率
- JVM内存使用情况（堆内存、GC次数）

【中间件监控】
- MySQL：连接数、慢查询、QPS
- Redis：内存使用、命中率、连接数
- RabbitMQ：队列长度、消息堆积、消费速度

【告警配置】
- 接口响应时间 > 1秒
- 接口错误率 > 5%
- 服务不可用
- 队列消息堆积 > 1000

【Grafana仪表板】
- 系统概览：所有服务的健康状态
- 服务详情：单个服务的详细指标
- 中间件监控：数据库、缓存、消息队列
- 告警历史：历史告警记录和处理情况
```

### 💡 中频问题（可能问）

#### 11. 如果某个微服务挂了，怎么快速定位和恢复？

**回答要点：**
```
【快速定位】
1. 监控告警：Prometheus告警通知服务不可用
2. 查看日志：
   - docker logs 查看容器日志
   - Kibana查看应用日志
   - 看是启动失败还是运行时错误
3. 检查依赖：
   - 检查数据库、Redis、RabbitMQ是否正常
   - 检查Nacos服务注册情况
4. 查看资源：
   - 服务器CPU、内存、磁盘是否正常
   - 容器资源限制是否合理

【快速恢复】
1. 重启服务：docker-compose restart service-name
2. 如果重启无效，回滚到上一个版本
3. 如果是资源问题，扩容或优化资源配置
4. 如果是代码bug，紧急修复后重新部署

【预防措施】
- 配置健康检查，自动重启异常容器
- 部署多个实例，一个挂了其他继续服务
- 配置熔断降级，避免级联故障
```

#### 12. 如何保证部署过程中服务不中断？

**回答要点：**
```
【滚动更新策略】
1. 先部署一个实例，验证正常
2. 逐步替换其他实例
3. 保证始终有实例在运行

【具体实施】
- 使用Nginx负载均衡，配置多个后端实例
- 更新时先下线一个实例
- 部署新版本，健康检查通过后加入负载均衡
- 依次更新其他实例

【零停机部署】
- 新旧版本同时运行一段时间
- 确认新版本稳定后，下线旧版本
- 如果新版本有问题，快速回滚

【我们的实践】
- 配置了健康检查接口
- Nginx自动摘除不健康的实例
- 部署时逐个更新，保证服务连续性
```

## 二、wfh-ELK 日志分析系统项目

### 🔥 高频问题（必问）

#### 1. 为什么要搭建ELK日志系统？

**回答要点：**
```
【传统日志的问题】
- 日志分散在各个服务器，查询困难
- 日志量大，手动查找效率低
- 无法实时监控和分析
- 故障排查慢，影响业务

【ELK的优势】
- 统一收集：所有日志集中存储
- 快速检索：秒级查询海量日志
- 实时分析：实时统计和分析
- 可视化：Kibana图表展示

【实际价值】
- 快速定位问题，故障排查效率提升
- 发现性能瓶颈，优化系统
- 监控业务指标，辅助决策
- 安全审计，追踪异常行为
```

#### 2. ELK的数据流转过程是怎样的？

**回答要点：**
```
【完整流程】
1. Filebeat采集日志
   - 监控日志文件变化
   - 读取新增的日志行
   - 发送到Kafka（或直接发送到Logstash）

2. Kafka缓冲（可选）
   - 作为消息队列缓冲
   - 解决日志高峰期堆积问题
   - 保证数据不丢失

3. Logstash处理
   - 从Kafka消费消息
   - 使用grok解析日志格式
   - 使用filter过滤和转换数据
   - 提取关键字段

4. Elasticsearch存储
   - 接收处理后的数据
   - 建立索引，支持快速检索
   - 分布式存储，支持海量数据

5. Kibana展示
   - 连接Elasticsearch
   - 提供搜索界面
   - 创建可视化图表和仪表板

【我们的架构】
Nginx/Tomcat日志 → Filebeat → Kafka → Logstash → Elasticsearch → Kibana
```

#### 3. Logstash的grok是怎么用的？

**回答要点：**
```
【grok的作用】
- 解析非结构化日志，提取结构化字段
- 使用正则表达式匹配日志格式
- 内置了很多常用的pattern

【Nginx日志解析示例】
原始日志：
192.168.1.100 - - [01/Jan/2024:10:00:00 +0800] "GET /api/articles HTTP/1.1" 200 1234

grok配置：
filter {
  grok {
    match => {
      "message" => "%{IP:client_ip} - - \[%{HTTPDATE:timestamp}\] \"%{WORD:method} %{URIPATHPARAM:request} HTTP/%{NUMBER:http_version}\" %{NUMBER:status} %{NUMBER:bytes}"
    }
  }
}

解析结果：
{
  "client_ip": "192.168.1.100",
  "timestamp": "01/Jan/2024:10:00:00 +0800",
  "method": "GET",
  "request": "/api/articles",
  "http_version": "1.1",
  "status": "200",
  "bytes": "1234"
}

【Java异常日志解析】
- 使用multiline插件合并多行日志
- 使用grok提取异常类型、堆栈信息
- 方便统计异常类型和频率

【实际应用】
- 解析Nginx访问日志，统计访问量、响应时间
- 解析应用日志，提取错误信息
- 解析慢查询日志，优化SQL
```

#### 4. Elasticsearch集群是怎么配置的？

**回答要点：**
```
【集群架构】
- 3个节点（1主2从，或3个master-eligible节点）
- 每个索引配置分片和副本

【配置要点】
1. 集群名称：所有节点相同的cluster.name
2. 节点角色：
   - master节点：管理集群
   - data节点：存储数据
   - 可以一个节点同时担任多个角色

3. 分片配置：
   - 主分片：5个（根据数据量调整）
   - 副本分片：1个（每个主分片1个副本）

4. 内存配置：
   - JVM堆内存设置为物理内存的50%
   - 最大不超过32GB

【索引管理】
- 按天创建索引：logs-2024.01.01
- 使用索引模板自动创建
- 定期删除旧索引，释放空间

【优势】
- 高可用：节点故障不影响服务
- 高性能：数据分片，并行查询
- 可扩展：增加节点即可扩容
```

#### 5. 为什么要引入Kafka？

**回答要点：**
```
【遇到的问题】
- 日志高峰期，Logstash处理不过来
- 日志堆积，甚至丢失
- Filebeat直接发送到Logstash，压力大

【Kafka的作用】
1. 削峰填谷：
   - 高峰期日志先存到Kafka
   - Logstash按自己的速度消费
   - 避免Logstash过载

2. 解耦：
   - Filebeat和Logstash解耦
   - 一方故障不影响另一方

3. 持久化：
   - Kafka持久化消息
   - 保证数据不丢失

4. 扩展性：
   - 可以增加Logstash实例并行消费
   - 提高处理能力

【架构对比】
之前：Filebeat → Logstash → ES
现在：Filebeat → Kafka → Logstash → ES

【效果】
- 日志高峰期不再堆积
- 数据不丢失
- 系统更稳定
```

#### 6. 如何保证日志数据的安全性？

**回答要点：**
```
【访问控制】
1. Elasticsearch RBAC：
   - 创建不同角色（admin、developer、viewer）
   - 分配不同权限（读、写、删除）
   - 用户绑定角色

2. Kibana用户管理：
   - 不同用户看不同的索引
   - 敏感日志只有管理员能看

【数据加密】
- 传输加密：使用HTTPS/TLS
- 存储加密：敏感字段脱敏

【备份策略】
- 定期快照备份
- 保留最近7天的数据
- 重要日志长期归档

【审计日志】
- 记录谁访问了什么数据
```

## 四、可能的追问

### 关于技术细节

1. **Docker和虚拟机有什么区别？**
   - 虚拟机：虚拟化硬件，包含完整OS，资源占用大，启动慢
   - Docker：虚拟化操作系统，共享宿主机内核，轻量级，启动快

2. **Redis为什么快？**
   - 内存存储，读写速度快
   - 单线程，避免上下文切换
   - IO多路复用，高效处理并发
   - 数据结构简单高效

3. **MySQL主从延迟怎么解决？**
   - 优化网络，减少延迟
   - 并行复制，提高同步速度
   - 重要数据读主库
   - 使用半同步复制

4. **如何保证消息不丢失？**
   - 生产者：开启确认机制
   - Broker：持久化消息
   - 消费者：手动ACK

5. **Elasticsearch为什么快？**
   - 倒排索引，快速定位
   - 分片并行查询
   - 缓存机制
   - 优化的数据结构

### 关于问题排查

1. **服务突然变慢，怎么排查？**
   - 查看监控：CPU、内存、网络
   - 查看日志：是否有错误
   - 查看数据库：是否有慢查询
   - 查看缓存：命中率是否下降
   - 查看依赖服务：是否正常

2. **内存泄漏怎么排查？**
   - 使用jmap dump堆内存
   - 使用MAT分析内存占用
   - 找出占用内存最多的对象
   - 分析代码，找出泄漏点

3. **CPU使用率突然飙高怎么办？**
   - top查看是哪个进程
   - top -Hp查看是哪个线程
   - jstack查看线程堆栈
   - 分析是死循环还是GC频繁

### 关于优化

1. **如何优化Docker镜像大小？**
   - 使用精简的基础镜像（alpine）
   - 多阶段构建
   - 清理不必要的文件
   - 合并RUN命令，减少层数

2. **如何优化MySQL查询性能？**
   - 添加索引
   - 优化SQL语句
   - 分库分表
   - 读写分离
   - 使用缓存

3. **如何提高系统并发能力？**
   - 增加服务器实例
   - 使用缓存减少数据库压力
   - 异步处理非核心业务
   - 使用消息队列削峰填谷
   - 优化代码，减少响应时间

## 五、面试技巧

### 回答问题的STAR法则

- **S (Situation)**: 说明背景和情境
- **T (Task)**: 说明你的任务和目标
- **A (Action)**: 说明你采取的行动
- **R (Result)**: 说明最终的结果和收获

### 注意事项

**✅ 应该做的：**
- 回答要有逻辑，结构清晰
- 用数据说话，量化结果
- 突出自己的贡献
- 展现思考过程
- 诚实回答，不懂就说不懂
- 准备好追问

**❌ 避免的：**
- 回答太笼统，没有细节
- 只说"我们"，不说"我"
- 夸大自己的作用
- 背答案，不理解原理
- 遇到不会的硬扯
- 说话没有重点

### 加分项

1. **主动思考**：不只是完成任务，还思考为什么这么做
2. **持续优化**：不满足于现状，持续改进
3. **文档意识**：注重文档编写和知识沉淀
4. **团队协作**：能和团队良好沟通协作
5. **学习能力**：快速学习新技术的能力
6. **问题意识**：能发现问题并主动解决

### 如果遇到不会的问题

**好的回答方式：**
```
这个问题我之前没有深入研究过，但我了解大概的原理是...
如果让我来解决，我会先...然后...
我会在工作中深入学习这方面的知识。
```

**不好的回答方式：**
```
这个我不会
这个我没用过
这个我不知道
```

面试结束时，可以问面试官：

   - 这个岗位主要负责哪些工作？
   - 团队目前的技术栈是什么？
   - 有什么技术挑战？

2. **关于团队**：
   - 团队规模和结构是怎样的？
   - 团队的工作氛围如何？
   - 对新人有什么培养计划？

   - 有什么晋升通道？
   - 有技术分享和学习的机会吗？

4. **关于反馈**：
   - 您觉得我今天的表现怎么样？
   - 有什么需要改进的地方？
   - 后续流程是怎样的？
